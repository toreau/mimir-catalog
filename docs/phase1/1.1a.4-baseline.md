# Phase 1.1A.4 — SQLite Candidate A baseline (1.1A.4a)

Frozen Candidate A baseline for the storage bake-off. This foundation slice
freezes the physical baseline and the candidate-neutral adapter boundary; it
contains no corpus build and no benchmark.

## Candidate

Name `sqlite-native-v1`. Provider `Microsoft.Data.Sqlite` 10.0.11 (the package
line already used in this repository); the runtime SQLite library version is
captured as evidence at execution, never assumed.

## Physical schema

Four STRICT tables; `concept` uses an INTEGER PRIMARY KEY rowid alias; the other
three tables are plain rowid tables with no PRIMARY KEY or UNIQUE constraint so
duplicate multiplicity stays exactly representable.

```text
concept(Qid INTEGER PRIMARY KEY, InT1 INTEGER NOT NULL, InT2 INTEGER NOT NULL) STRICT
lexical_entry(Qid INTEGER NOT NULL, Lang TEXT NOT NULL COLLATE BINARY,
              LexKind TEXT NOT NULL COLLATE BINARY, Value TEXT NOT NULL COLLATE BINARY) STRICT
instance_of(SubjectQid INTEGER NOT NULL, TargetQid INTEGER NOT NULL) STRICT
subclass_of(SubjectQid INTEGER NOT NULL, TargetQid INTEGER NOT NULL) STRICT
```

## Indexes

Four reviewed secondary indexes, all non-unique:

```text
lex_lang_value ON lexical_entry (Lang COLLATE BINARY, Value COLLATE BINARY)   -- S2
lex_qid         ON lexical_entry (Qid, Lang COLLATE BINARY, LexKind COLLATE BINARY) -- S3, A5 labels
inst_subject    ON instance_of (SubjectQid, TargetQid)                        -- S4, G2
sub_subject     ON subclass_of (SubjectQid, TargetQid)                        -- S5, G1, G2
```

Reverse `TargetQid` edge indexes are intentionally excluded from the baseline
(edge heaps are narrow; served by thin full scans for A3/A4/A5). There is no
normalized lexical column or index.

## Raw lexical semantics

S2 is exact raw `Lang + Value`: BINARY collation declared on columns and indexes,
case-sensitive, no NOCASE, no normalization, no derived lookup key. `LexKind` is
result data. The later harness canonicalizes/sorts all results before digesting,
so SQLite ordering is never semantic.

## PRAGMA baseline

Build: `page_size = 4096`, `journal_mode = OFF`, `synchronous = OFF`,
`foreign_keys = OFF`, `automatic_index = OFF` (explicit), `temp_store = DEFAULT`
(unset). Not set: `cache_size`, `mmap_size`, `temp_store_directory` (prohibited,
deprecated). Not run: `ANALYZE`, `VACUUM`, `PRAGMA optimize`.

Read/benchmark connections are read-only and explicitly apply
`foreign_keys = OFF` and `automatic_index = OFF`; SQLite defaults are not relied
upon.

## Config identity

Tracked `benchmarks/candidate-a-sqlite-v1.json` freezes the full performance-
relevant baseline (schema, organizations, collations, indexes, build/read
PRAGMAs, policies, provider identity, corpus ID, workload ID). Candidate Config
ID is the full lowercase SHA-256 over a canonical semantic encoding; JSON
whitespace/ordering never defines it, and changing a normative value changes the
ID. Config ID is separate from the workload ID.
